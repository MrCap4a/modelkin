# Contributing

## Branch strategy

- `main` — всегда деплоится, защищена (никаких прямых push).
- Рабочие ветки — `feature/<кратко-суть>`, `fix/<кратко-суть>`,
  `chore/<кратко-суть>`. Одна ветка — одна логически завершённая задача.
- Ветка сливается через PR после прохождения CI.

## Коммиты

Коммит отражает одно логическое изменение — не собирайте несколько
несвязанных правок в один коммит и не делайте один гигантский коммит на
весь модуль (ТЗ §72). Сообщение — в повелительном наклонении, кратко что и
зачем:

```text
Добавить проверку владения моделью перед выдачей signed download URL
Исправить идемпотентность создания ownership при повторном webhook
```

## Перед тем как открыть PR

```bash
npm run typecheck
npm run lint
npm run test
npm run build
```

Все четыре команды обязаны проходить локально — CI повторяет их же.

## Требования к PR

- Описание: что изменилось и почему (не только "что").
- Затронутые модули/маршруты — что физически поменялось.
- Тесты: какие добавлены/обновлены; если тестов нет — почему (например,
  чисто документационное изменение).
- Известные ограничения/TODO, если есть.
- Скриншот/видео для UI-изменений, если применимо — визуальное соответствие
  дизайн-макету (design.pdf) обязательно для страниц, реализующих
  конкретный экран оттуда.

## Code style

- TypeScript strict — `any` не используется без явного, обоснованного
  исключения.
- ESLint + Prettier обязательны (`npm run lint`, `npm run format`).
- Небольшие, ответственные функции — если функция делает больше одной вещи,
  разделите её.
- Никаких `console.log` в production-коде — используйте
  `getLogger()`/`recordAuditEvent()` (см. [LOGGING.md](./LOGGING.md)). CLI-скрипты
  (`prisma/seed.ts`, `src/infrastructure/jobs/worker.ts`) — исключение,
  там console — часть UX.
- Никакого неиспользуемого кода — ESLint (`@typescript-eslint/no-unused-vars`)
  ловит большинство случаев, но проверяйте и вручную (мёртвые
  экспорты/файлы).

## Архитектурные правила (обязательны к соблюдению)

Подробности — [ARCHITECTURE.md](./ARCHITECTURE.md). Коротко:

- Presentation → Application → Domain → Infrastructure, никогда наоборот.
- Domain не импортирует Next.js/React/Prisma/S3/конкретный платёжный SDK.
- Другие модули импортируются только через их `index.ts` (публичный
  контракт модуля), никогда напрямую из чужого `application/*` или
  `infrastructure/*`.
- Никаких циклических зависимостей между модулями.
- Не создавайте общий `utils/`/`services/`, куда сваливается всё подряд —
  новый код относится к конкретному модулю или к `shared/` только если это
  действительно кросс-модульная утилита без бизнес-логики.

## Параллельная работа / несколько агентов

Если несколько разработчиков (или AI-агентов) работают одновременно (ТЗ
§69-71):

- Заранее определите зону ответственности (какие модули/директории каждый
  трогает).
- Никогда не редактируйте одновременно без координации: `package.json`,
  `prisma/schema.prisma`, `src/middleware.ts`, `src/shared/config/**`,
  общие компоненты (`src/components/shared/**`) — эти файлы меняются
  централизованно, изменения в них согласуются отдельно.
- По завершении параллельной работы — обязательная интеграция: merge →
  `typecheck` → `lint` → `test` → `build` → `test:e2e`, конфликты
  разрешаются явно, а не оставляются на усмотрение следующего разработчика.

## Тестирование

Новая функциональность обязана иметь тесты соответствующего уровня — см.
[TESTING.md](./TESTING.md). Фича без server-side валидации, обработки
ошибок, loading/empty state и покрытия тестами не считается готовой (ТЗ
§74).
