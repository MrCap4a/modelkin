# Моделкин.рф

## Техническое задание на разработку полноценного production-ready IT-продукта

---

# 1. Задача

Разработать полноценный веб-сервис **Моделкин.рф** — интернет-магазин цифровых 3D-моделей в формате STL.

Для разработки предоставляются:

1. этот документ;
2. PDF-файл с дизайнами экранов.

## Источники требований

### PDF

PDF является источником истины для:

* визуального дизайна;
* расположения элементов;
* структуры экранов;
* компонентов;
* визуальных состояний;
* типографики;
* цветов;
* размеров;
* responsive-поведения, если оно представлено.

### Данное ТЗ

Данное ТЗ является источником истины для:

* функциональности;
* бизнес-логики;
* архитектуры;
* структуры данных;
* безопасности;
* хранения файлов;
* авторизации;
* тестирования;
* логирования;
* deployment;
* технических требований.

---

# 2. Главная цель

В результате должен получиться **не прототип и не демонстрационный frontend**, а полноценный поддерживаемый IT-продукт, который можно:

* запустить локально;
* запустить через Docker;
* развернуть на сервере;
* обновлять;
* тестировать;
* диагностировать;
* сопровождать;
* расширять новыми функциями.

Другой разработчик, изучив репозиторий и документацию, должен понимать:

* как устроен проект;
* как запустить его;
* как изменить код;
* как устроена БД;
* как работает авторизация;
* как работают заказы;
* где хранятся файлы;
* где искать логи;
* как делать backup;
* как выполнять deployment;
* как добавлять новые функции.

---

# 3. Правила работы с PDF

Перед реализацией необходимо **полностью изучить PDF**.

Составить внутреннюю карту:

```text
экран
→ route
→ пользовательский сценарий
→ компоненты
→ данные
→ действия
→ состояния
```

Необходимо определить все представленные экраны.

---

# 4. Правило вопросов

Если в PDF и функциональном ТЗ есть неоднозначность, действовать следующим образом.

## Вопрос задавать только если:

неопределённость **существенно влияет на пользовательский опыт или бизнес-логику**.

Например:

* непонятно, может ли гость купить модель;
* непонятно, куда попадает пользователь после оплаты;
* два экрана предполагают разное поведение;
* непонятно, какое действие совершает кнопка;
* невозможно определить обязательность важного поля;
* существуют противоречивые бизнес-правила.

## Не спрашивать:

* какую библиотеку использовать;
* какую ORM использовать;
* как назвать файл;
* как организовать внутренний модуль;
* как сделать API;
* как хранить данные;
* какой Docker image использовать;
* как оптимизировать запрос;
* какой способ кеширования выбрать.

Это инженерные решения, которые должен принимать разработчик самостоятельно.

# 5. Архитектура

Использовать **модульный монолит**.

Это осознанный выбор между:

* простым монолитом без структуры;
* микросервисами.

Микросервисную архитектуру сейчас НЕ использовать.

Но внутренние границы модулей должны быть такими, чтобы отдельный модуль при необходимости можно было впоследствии вынести в сервис.

# 7. Почему модульный монолит

Приложение должно иметь следующую концепцию:

```text
                    ┌───────────────────────┐
                    │       Next.js         │
                    │                       │
                    │  Presentation         │
                    │        ↓              │
                    │  Application          │
                    │        ↓              │
                    │  Domain               │
                    │        ↓              │
                    │  Infrastructure       │
                    └──────────┬────────────┘
                               │
             ┌─────────────────┼─────────────────┐
             ↓                 ↓                 ↓
        PostgreSQL            S3             External APIs
```

Никогда не использовать floating point для денежных значений.

Хранить:

```text

```

в минимальных денежных единицах.

Например:


# 22. Корзина

Цифровые товары не имеют quantity.

Правила:

* одна модель = одна позиция;
* купленную модель нельзя добавить;
* удаление работает;
* total рассчитывается сервером.

**Никогда не доверять total, который прислал frontend.**

---

# 23. Orders

Создание заказа:

```text
Cart
 ↓
server validates cart
 ↓
server gets actual prices from DB
 ↓
creates Order
 ↓
creates OrderItems
 ↓
creates Payment
```

Frontend не определяет стоимость заказа.

---

# 24. Payments

Реальный платёжный провайдер пока НЕ подключать.

Но создать интерфейс:

```text
interface PaymentProvider {
    createPayment(...);
    getPaymentStatus(...);
    verifyWebhook(...);
    handleWebhook(...);
}
```

Сделать mock/test implementation.

Позже реальный provider должен подключаться через Infrastructure layer.

Бизнес-логика заказа не должна знать конкретный SDK платёжной системы.

---

# 25. Payment flow

Архитектурно:

```text
Cart
 ↓
Order PENDING_PAYMENT
 ↓
Payment PENDING
 ↓
external provider
 ↓
webhook
 ↓
verify webhook
 ↓
Payment PAID
 ↓
Order PAID
 ↓
create ownership
```

Создание ownership должно быть идемпотентным.

Повторный webhook не должен создавать дубли.

# 33. Хранение логов

Логи должны сохраняться **в файлы посуточно**.

Например:

```text
logs/
├── 2026-09-18/
│   ├── application.log
│   ├── error.log
│   └── audit.log
│
├── 2026-09-19/
│   ├── application.log
│   ├── error.log
│   └── audit.log
```

Или эквивалентная реализация с ежедневной ротацией.

Требования:

* автоматическая daily rotation;
* отдельный error log;
* отдельный audit log;
* timestamp;
* requestId/correlationId;
* возможность найти событие по ID;
* корректная работа при рестарте контейнера.

# 35. Docker environments

Предусмотреть как минимум:

```text
development
production
```

Development:

```text
Next.js
PostgreSQL
S3-compatible storage
```

При необходимости можно использовать локальный S3-compatible сервис, например MinIO.

Production:

```text
Next.js container
PostgreSQL
```

Не обязательно запускать production PostgreSQL внутри того же Compose-файла, если инфраструктура сервера предусматривает отдельную БД.

Архитектура должна позволять оба варианта.

# 41. Request ID

Каждый HTTP request должен иметь:

```text
requestId
```

Если клиент передал корректный correlation/request ID — его можно сохранить, иначе генерировать новый.

Request ID должен присутствовать в:

* application logs;
* error logs;
* важных audit events.

Это необходимо для диагностики проблем.

# 43. Security headers

Настроить необходимые HTTP security headers.

Минимально рассмотреть:

* Content-Security-Policy;
* X-Content-Type-Options;
* Referrer-Policy;
* frame protection;
* permissions policy;
* HSTS для production.

Конкретные значения подобрать с учётом работы 3D viewer, images и S3.

---

# 44. Rate limiting

Добавить rate limiting как минимум для:

* login;
* registration;
* password reset;
* sensitive API;
* file upload endpoints.

Конкретный механизм выбрать самостоятельно с учётом Docker/deployment architecture.

---

# 45. CSRF

Проверить необходимость CSRF protection для всех state-changing операций.

Если используется исключительно подход, защищающий операции через same-origin + appropriate cookies/headers, задокументировать выбранную модель.

Не просто отключать защиту.

---

# 46. File security

Для загрузок:

* ограничить размер;
* валидировать MIME;
* валидировать extension;
* генерировать безопасные storage keys;
* не использовать оригинальное имя файла как storage path;

# 64. Idempotency

Критические операции должны быть идемпотентными там, где это необходимо.

Особенно:

* payment webhook;
* payment confirmation;
* ownership creation;
* повторная загрузка;
* повторная обработка background jobs.

---

# 65. Transactions

Использовать database transactions там, где несколько изменений должны происходить атомарно.

Например:

```text
Payment confirmed
 ↓
Order PAID
 ↓
Ownership created
```

Эти операции должны быть согласованы.

---

# 66. Concurrency

Учитывать race conditions.

Например:

два запроса одновременно пытаются добавить/купить одну модель.

Database constraints должны дополнительно защищать бизнес-правила.

Не полагаться только на frontend.

---

# 67. Background jobs

Если в реализации появятся операции, которые не должны выполняться в HTTP request:

* email;
* обработка файлов;
* генерация preview;
* тяжёлая обработка STL;

предусмотреть abstraction для background jobs.

Не добавлять Redis/BullMQ или другую очередь только ради самой очереди.

Если она действительно потребуется — выбрать и документировать.

Архитектура должна позволять добавить worker без переписывания бизнес-логики.

# 68. STL preview

```text

 ↓

 ↓

 ↓

 ↓
update Model
```

Если на первом этапе это слишком тяжёлая инфраструктура, разрешается использовать загружаемый администратором preview.

Но архитектура должна позволять автоматизацию позже.

# 69. Работа нескольких агентов

Если используемая среда/Claude позволяет запускать несколько агентов параллельно, **использовать параллелизацию там, где задачи действительно независимы**.

Например:

```text
Agent A
→ database / Prisma

Agent B
→ authentication

Agent C
→ frontend/catalog

Agent D
→ testing/documentation
```

Но не допускать хаотического одновременного изменения одних и тех же файлов.

Перед параллельной работой определить ownership зон.

---

# 70. Координация агентов

Главный агент является ответственным за интеграцию.

Каждый sub-agent должен:

* получить чёткую область ответственности;
* не менять чужую область без необходимости;
* сообщить изменённые файлы;
* сообщить тесты;
* сообщить известные проблемы;
* не ломать архитектурные правила.

После завершения параллельных задач главный агент обязан:

1. объединить изменения;
2. запустить typecheck;
3. lint;
4. tests;
5. build;
6. E2E;
7. исправить integration issues.

---

# 71. Нельзя распараллеливать бездумно

Не запускать нескольких агентов, если они одновременно редактируют:

```text
package.json
schema.prisma
shared config
same component
same migration
```

без координации.

При конфликте главный агент обязан разрешить его, а не оставлять проект в неопределённом состоянии.
